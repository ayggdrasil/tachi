# GPT review — round 2 (gpt-6.1-sol, reasoning xhigh)

**Scores:** demo_readiness 6.8 · senior_ux 7 · family_ux 7.5 · ai_behavior 6.5 · robustness 5.5 · design_fidelity 8.2 · overall 7

The captures demonstrate a complete offline flow through memory creation, sharing, recall, itinerary generation, scheduling, and reporting, with a strong graphite-on-paper visual foundation. Several round-1 fixes genuinely hold: new memories start private, consent parsing is narrower, trip offers are reserved to prevent duplicates, and non-unanimous scheduling results require confirmation. However, the mobile captures still bury the graph, privacy controls, and primary actions, while the Director has timing and state-management gaps that can derail a fast live run. Privacy enforcement remains incomplete across action authorization, live emissions, derived trip data, and historical messages, and the family health answer can contradict the newly added urgent-reading safeguards.

  - Problem: The most important demo moments are below the fold: the saved-memory graph and sharing controls, the recall path, and the itinerary's family actions are not visible when their steps complete.
  - Evidence: 05-senior-a-story.png shows only the photo and extracted fields before the composer starts at about y=630; the graph, visibility switch, and share actions are below it. 07-senior-recall.png cuts off the story before the matched path, and 08-senior-trip.png cuts off the third stop before either family CTA. MessageList pins long cards to their top, while ActionBar is rendered after the entire card. The consent quick replies are on the preceding text message, so the isLast check hides them once the memory card arrives.
  - Fix: Create compact initial card states sized for the available chat viewport: collapse graph/story details, shorten the initial itinerary preview, and place the consent or family CTA in an immediately visible action region. Show the graph automatically in the Director during memory creation. Add 390×844 screenshot assertions that each step's primary action is visible without scrolling.
- **F2 [high] demo** `web/src/pages/demo/DirectorConsole.tsx`
  - Problem: Fast manual advancement can send the trip acceptance before a trip offer exists, leaving the Director waiting for an itinerary that will never be generated.
  - Evidence: The recall step completes on recall_card, not trip_suggestion. The following step immediately sends '좋아, 다시 가보고 싶네'. In senior.ts, scheduleOffer reserves the memory before its delayed callback, and offerTripFromIntent simply returns when offerReserved contains that memory. A fast share → recall → trip sequence can therefore consume the acceptance without accepting anything, followed by a 45-second Director timeout.
  - Fix: Gate the trip step on an actual actionable trip_suggestion and send accept_trip with its tripId. Alternatively, queue acceptance against the reserved offer rather than silently returning. Test rapid manual advancement with no dwell and with a delayed suggestTrip provider.
- **F3 [high] demo** `server/orchestrator/core.ts`
  - Problem: The virtual clock cannot reliably start the demo at 09:00 when the presentation happens after 09:00.
  - Evidence: setDemoClock compares the requested time with now(), which initially equals wall-clock time. If the target is earlier, it applies cur + 1 instead of the requested time. Starting at 16:00 and requesting the first scripted 09:00 greeting produces approximately 16:01, not 09:00. Subsequent report timestamps then differ from the rehearsed story.
  - Fix: Allow the first clock assignment after reset to establish an absolute demo time, independent of wall-clock time. Apply monotonicity only between subsequent scripted events. Add tests starting the application at afternoon and evening wall-clock times and assert the scripted 09:00, 14:10, 14:20, and 21:00 timestamps.
- **F4 [high] demo** `server/brain/llm.ts`
  - Problem: The revised provider timeout and circuit breaker still do not establish a credible 90-second live-provider budget.
  - Evidence: Each provider operation can wait 12 seconds, the breaker opens only after two failures, and it retries after 60 seconds. The script performs separate live operations for greeting, photo observation, interview turns, extraction, sharing, recall, suggestion, itinerary, health answer, gathering, and report, in addition to Director dwell time. A slow provider can consume a substantial fraction of the demo before fallback; STEP_TIMEOUT allows a single step to occupy 45 seconds.
  - Fix: Add a presentation-mode end-to-end deadline per step, preflight the selected providers before starting the timer, and fall back within a short explicit budget. Precompute or start expensive itinerary work earlier where appropriate. Run the full script with default pacing against delayed and failing provider stubs and assert completion within 90 seconds.
- **F5 [critical] server** `server/orchestrator/messages.ts`
  - Problem: A family member can invoke senior-only actions and publish or change another person's private memory without consent.
  - Evidence: handleAction checks membership in the supplied room, then routes every SENIOR_ACTIONS value to handleSeniorAction without checking the actor. handleSeniorAction permits a missing action entry and accepts client-supplied memoryId/tripId overrides. A jieun socket can use a family-room message ID with actionId='share_memory' and memoryId='mem-wedding-1976'; doShare has no owner authorization and changes that private memory to family visibility.
  - Fix: Authorize senior actions against the authenticated memory/trip owner and the correct senior room. Require the requested action to exist on the referenced message, and derive resource IDs from its server-stored action data rather than arbitrary client overrides. Add adversarial socket tests using a valid family identity and a family message.

  - Evidence: Sidebar renders '어머니 화면 보기' linking to /senior?as=mom. resolvePersona accepts that query parameter, and hello accepts mom without an owner credential. - **F7 [high] server** `server/orchestrator/core.ts`

  - Evidence: post and updateMessage broadcast the stored message directly to the room channel instead of applying projectMessage and scrubHiddenTitles. When the memory category is private, require explicit resolution of that setting rather than reporting successful sharing while bootstrap and live delivery disagree.

- **F10 [high] server** `server/orchestrator/core.ts`
  - Problem: The generation guards do not fully prevent old asynchronous work from contaminating a reset.
  - Evidence: installGuards checks staleness only when graph.upsertMemory is entered. - **F11 [high] ai** `server/brain/heuristics/family.ts`

Evaluate the latest systolic and diastolic readings before averages, and suppress reassuring bot templates for concerning readings. Add a regression covering a 200/120 latest reading with an otherwise normal seven-day history.
